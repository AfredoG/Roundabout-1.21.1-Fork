## Как открыть и проверить

Установите JDK 21 и Git. Для помощника обновлений нужен Python 3.10 или новее.
В IntelliJ IDEA откройте **папку neoforge** как Gradle-проект и выберите JDK 21
для Gradle JVM. Корневой Gradle-проект — оставшаяся конфигурация автора под 1.20.1;
его не нужно запускать для сборки этого порта. Fabric в данной ветке не поддерживается.

Windows PowerShell:

```powershell
cd neoforge
.\gradlew.bat compileJava processResources
```

Linux:

```bash
cd neoforge
bash gradlew compileJava processResources
```

Сейчас `compileJava` завершается ошибками. После завершения переноса используются
`build`, `runClient` и `runServer`; эти команды не являются подтверждением готовности
текущего архива. Первый запуск Gradle требует интернета для зависимостей.

## Как переносить обновления автора

Архив содержит Git-репозиторий с исходной базой и коммитами переноса.
Папку `.git` нужно сохранить. История до исходной базы сокращена для размера архива;
при необходимости её можно получить командой `git fetch --unshallow upstream`.
Новый публичный fork на GitHub не создавался, изменения никуда не опубликованы.

Команды выполняются из корня RoundaboutMod. Сначала сохраните свои изменения
коммитом. При первом использовании Git настройте своё имя и email для коммитов.

Показать изменения в master без изменения рабочей ветки:

```bash
python port/update_upstream.py
```

Создать отдельную ветку и попытаться объединить обновление:

```bash
python port/update_upstream.py --apply
```

Можно выбрать тег или коммит автора вместо master:

```bash
python port/update_upstream.py --ref ИМЯ_ТЕГА --apply
```

Помощник не делает push и не создаёт финальный коммит. Он оставляет слияние для
проверки. При конфликте выполните `git status`, исправьте конфликтующие файлы,
обновите `base_commit` в `port/upstream.json` до показанного Candidate после
успешного разрешения и проверьте сборку. Если слияние было чистым, поле обновляется
самим помощником. Затем проверьте клиент и выделенный сервер, просмотрите
`git diff HEAD`, добавьте проверенные изменения через `git add` и выполните
`git commit`. Для отмены используйте `git merge --abort`; если помощник изменил
метаданные базы, восстановите их через `git restore port/upstream.json`.

Git rerere запоминает разрешения конфликтов; повторные решения всё равно нужно
проверять. При добавлении новых API-зависимых механик автором потребуется ручная
адаптация. Помощник автоматизирует получение и слияние изменений, а не перевод
любого будущего кода Minecraft 1.20.1 в 1.21.1.

## Проверка на GitHub

В `.github/workflows/neoforge.yml` находится workflow сборки. Он станет доступен,
когда проект будет помещён в ваш репозиторий GitHub. Текущая компиляция не проходит,
поэтому workflow сейчас также должен завершаться ошибкой, а не выдавать рабочий JAR.
Для публикации готового порта необходимы отдельно успешная сборка и игровые проверки.
